# Keenable 0.3 upgrade, flagged outcome rules R1–R7, and v2 merge into the staged site export

PR #107 does three things. It moves Keenable from 0.1.3 to 0.3.0 and adds search/fetch options. It adds flagged outcome rules R1–R7 so the candidate audit can publish open-ended, in-progress, delivery-only and undecided records. It adds `docs/export_data.py --v2-db`, which merges v2-published promises into a staged export. With the flags off, the audit path is unchanged. Tests: 806 passed with flags off. With `SF_PROMISES_OUTCOME_RULES=1` and `SF_PROMISES_DATE_RESOLUTION=1`, the outcome, merge, date and mutation tests pass (120). The full suite with both flags on has the 3 failures the PR already lists.

On the candidate path, no verdict is published without a verified verbatim origin quote, and `kept` needs a verified delivery sentence. The site-merge path re-hashes sources and re-finds quotes, but it does not check that a verdict has the evidence it needs. The schema change breaks flagged runs on existing v2 databases, and the merge rejects the open-ended and short-horizon records that R1/R2 create.

Watch for: (1) the merge accepts any verdict with an ORIGIN row, so `kept` or `broken` can reach the site with no delivery or contrary evidence (confirmed); (2) `UNDECIDED` and NULL deadline fail on existing v2 databases at publish time, with no preflight (confirmed by experiment); (3) merge rejects every R1/R2 record, so those never reach the site (confirmed); (4) R2 disables the short-horizon check for any deadline 0–59 days out (confirmed); (5) `broken` from one `NOT_DELIVERED` sentence with no date check against the deadline (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

On the candidate path the publication gates hold. The ORIGIN evidence row is always built from `candidate.promise_text`, `record_preliminary_evidence` must return `recorded` against saved bytes, and `build_snapshot` re-verifies at export. R4 `kept` requires the delivery phase in `relied_phases`, so the verifier must confirm it and a verified delivery quote is stored. Advocate states only count when their own selected sentence exists, which closes the "claimed delivery with no sentence" hole. With the flag off, the changed branches reduce to the old code. The rubric changes only matter when `deadline is None`, and a test pins the old prompts.

The rules widen what is publishable in three ways that need attention. R2 as implemented drops the short-horizon check entirely for deadlines up to 59 days after the promise. `CONTRARY` lets one `NOT_DELIVERED` sentence produce `broken`, where the standard rubric also needed a survival sentence, and nothing ties that sentence's date to the deadline. R3/R5 publish with ORIGIN-only evidence, which the PRD allows, but the "not checked / open-ended / no evidence found" labels live only in an `outcome_basis` row that the site merge does not carry over.

The merge is the last gate before the public site and it is weaker than the candidate path. It re-hashes every cited source and re-finds every quote, and it only appends. It never checks verdict against evidence phase or the verifier rows. It also hard-codes `passed: True` checks. It rejects every NULL-deadline record and does not apply R2, so the new rules and the merge do not work together.

The schema edit lands in `CREATE TABLE IF NOT EXISTS` without a version bump. New flag-off databases lose two backstops (NOT NULL deadline, verdict CHECK), and existing databases fail at the final insert when a flagged run tries to publish.

Keenable retries are bounded per call and the SDK's own retries are off. Two second-order effects are worth fixing: result and fetch counts triple with no aggregate budget, and `max_chars=400000` grows the archive while extraction still reads only the first 10,000 characters.

### Site merge publishes by provenance, not by verdict support

`_load_promise` in `src/site_merge.py` re-hashes every evidence file and re-finds every quote through `screen_saved_source`. It then needs one ORIGIN row whose quote contains `promise_text` and passes `check_origin_dates`. That answers "can the merge publish a record whose source hash or quote fails": no. It does not answer whether the verdict is supported. A `KEPT` row with only an ORIGIN row passes, as does a `BROKEN` row with no contrary evidence, and a row with no `independent_verifier` verification. The flagged pipeline can legitimately produce ORIGIN-only `in_progress` and `undecided`, so the rule cannot be "all three phases". It can be per verdict: delivery evidence for the kept family, contrary evidence for `broken`. `build_record` then hard-codes `all_checks_passed: True`, `failed_check_count: 0` and `has_contradictory_evidence: False` (lines 391, 401), and every entry in `checks` is `passed: True` regardless of what ran. Confidence: confirmed by reading; tests in `tests/test_export_v2_merge.py` cover tampered or missing sources and duplicates but not verdict/evidence mismatch. `VERDICT_MAP` also maps `STALLED`, which the schema CHECK does not allow (line 29, dead entry).

Existing records are not altered: the merge appends records and updates `database_status` counts, `tracked_count`, `discrepancies` and `id_reconciliation`. Legacy records for an entity that also gets a new v2 record keep their old `entity_promise_count`, so the counts shown across one entity's records can disagree (low).

### Open-ended and short-horizon records cannot reach the site

The merge returns `promise_date_invalid` when `deadline is None` (line 157). It calls `check_origin_dates` without the R2 filter (line 187), so a record whose deadline is 0–59 days out is rejected as `origin_evidence_missing`. R1 and R2 records, and the open-ended `undecided` that R1+R5 produces, are therefore rejected at merge. It fails closed and the PR text does not say it. The reverse problem exists in `src/export.py`: `_origin_date_failures` depends on the environment flag at export time. A flagged database exported with the flag unset raises "Missing valid origin evidence" and aborts the entire snapshot (`test_snapshot_rejects_open_ended_when_flag_off` documents this). Fail-closed, but all-or-nothing, and it depends on an environment variable the data does not carry. Confidence: confirmed.

### R2 as written is wider than "one-off dated event"

`promise_horizon_short` fires only when `deadline - promised < 60` days (`src/temporal.py:87`). R2 ignores it whenever `deadline >= promised` (`src/outcome_rules.py:36-38`), so the only horizons still rejected are negative ones. Any "within 30 days" commitment passes. The PRD text gives the same condition, with the one-off rationale in parentheses, but nothing checks that rationale. Confidence: confirmed.

### Contrary evidence staleness

`decide_outcome` returns `BROKEN` for `NOT_DELIVERED`, a passed deadline and survival in `UNKNOWN`/`NOT_YET_OPEN`, using one selected sentence (`src/outcome_rules.py:58-62`). The verifier sees the sentence's published date but no rule requires it to be on or after the deadline, so an article written before the deadline saying "not yet delivered" can support `broken`. The old path needed a second sentence (survival `NOT_YET_OPEN`), which is equally undated, so the new risk is smaller than it looks but the bar is lower. Confidence: likely.

### Schema change without migration

`schema.sql` is applied with `CREATE TABLE IF NOT EXISTS` and `PRAGMA user_version` stays at 4. Experiment: on a database built from main's schema, inserting a NULL deadline fails with `NOT NULL constraint failed: promises.date_deadline` and inserting `UNDECIDED` fails the CHECK. In `audit_candidate` the failing INSERT is inside `BEGIN IMMEDIATE` (`src/candidate.py:473-487`), so the transaction rolls back and the exception propagates out of the audit. The preliminary evidence and relevance rows were written before the transaction, so what remains in the database after the rollback should be checked. The README admits the migration is needed but nothing checks for it at start-up. Conversely, new databases built flag-off no longer reject NULL deadlines or `UNDECIDED`, so the database stops backstopping the flag. Open question for the author: since `user_version` is unchanged, `open_v2_database` in the merge accepts both shapes, so the merge cannot tell which rule set produced a database.

### Gold gate rebaseline

`data/gold_gate_expectations.json` replaces the recorded hash of `src/lifecycle_rubric.py`. The rubric diff is behavior-preserving for non-None deadlines (the new branches key on `no_deadline`), and `test_exhaustive_safety_of_rubric` covers the combinations, but the guard exists to flag edits to this file and it was updated in the same change. Confidence: confirmed that the baseline moved; the semantic equivalence check passed.

### Outcome labelling and derived dates

`outcome_basis` is exported in `build_snapshot` but `build_record` in the merge drops it. A merged `kept` carries "current status not checked" only as a suffix in `verdict_reason`, and an R5 `undecided` or R3 `in_progress` has nothing saying why. The PRD (R7) wants the basis recorded; the site loses it. Open-ended `kept` via `DELIVERED_ON_TIME` and no deadline is "on time" against nothing (`outcome_rules.py:83-84`); consider labelling it delivered-without-deadline. Confidence: confirmed for the dropped field.

### Keenable retries, per-page errors, cards, archive size

`RetryingKeenable._request` makes at most 3 attempts, sleeps at most 30 seconds per retry, refuses `Retry-After` over 30 seconds, and `max_retries=0` disables the SDK layer. `test_options_reach_the_wire_and_page_error_is_not_retried` shows one request per page error. The aggregate is not bounded: search results rose from 8 to 25 per phase and blocked URLs do not count toward the 3-source cap (`src/discovery.py:205`), so one candidate can try about 75 fetches, each worst case about 60 seconds of sleep plus timeouts. Confidence: likely. Per-page errors with status 502/503/504 inside a 200 response become `http_5xx` blocked entries without going through the transient retry (possible; depends on how Keenable reports them). `disable_cards=True` is hard-coded in `search_options` (`src/discovery_config.py:108`) while every other option comes from config; it only drops card-only results, which have no stable URL, so it does not risk provenance.

`fetch_max_chars=400000` is stored in full, but both `_source_segments` callers read `text[:10000]` (`src/extract.py:67`), so long agendas are archived and then analysed only in their first 10,000 characters. Worst case per candidate is about 9 pages × 400 KB (3.6 MB), against a current `data/sources` total of 7.6 MB across 21 promise directories. Confidence: confirmed for the 10,000-character read.

### Test coverage

Not tested: merge with verdict/evidence mismatch, merge with NULL deadline or `undecided`, merge across several databases, publishing into an old-schema database, and the 3 tests that assert flag-off behavior and fail with flags on (listed in the PR as open).
